# 单元文件夹

`gwb-unit-folder` 是 gwb 内核线的一个件。它管的是**「单元」这个纯目录约定在工作台里长什么样**：
容器根下一层一个目录、目录里一张 `unit.json` 出生证——这个件建单元、把它们画成一棵树（现扫、读证、按状态与种类过滤、
展开、看原文），并且**把「人现在看的是哪个单元」这个事实往外报**给别的件。出生证的字段表是本件的正本
（读盘与 `unit-folder.create` 共用一处校验），见 [服务面与命令面](/docs/service-and-commands#出生证-unitjson)。

这一页讲原理与模块划分；服务面、事件与命令面在 [服务面与命令面](/docs/service-and-commands)；
为什么是「往外报」而不是扩展点、置顶为什么从设置改成数据，在轨迹卡[「选中往外报」](/trajectory/2026-09-09-report-selection-not-extension-point)。

## 一次点击从头到尾怎么走

人在树格里点一个单元行。浏览器半做两件事：本地展开那一行（目录清单经 `unit-folder.listDir` 现拉）、
**fire-and-forget** 一条 `unit-folder.select { path }` 给宿主半。第二件事不等第一件，也不让第一件等它——
「当前单元」是给别的件看的，报不上去不该让树本身卡住。

宿主半收到 `select`：先过那堵墙——解设置里的 `units-root`、把参数路径验成容器根内的绝对路径——
再按路径形状推出所属单元（relative 的第一段就是单元名，不碰盘），记成「最近一次点击」；
如果 `current()` 因此变了，就在自己的 ctx 上 `emit('unit-folder/selection', …)`。消费方（第一个是文档站件）
早在挂载时局部注入了本件、`on` 了这条事件，于是它知道该换哪个单元的文档站了。

置顶走的是同一条墙，但落点不同：`unit-folder.pin { path }` 要求 path 是容器根下一层的单元目录，
追加进内存里那张置顶表、再写 `gwbData` 的文档 `pinned`（`{ paths }`）。置顶可以有多个；`current()` 没点过时回落到
第一个置顶，所以置顶在那种局面下也会让 `current()` 变、也会广播。

点的是文件就不报选中，而是开一格原文。原文格是外壳眼里的**文档窗格**（能多开，一份装一个文件），单元树是
**工具窗格**（整页一份）。两格之间不经总线：装哪个文件住在那一份原文格的参数里（key 是文件的绝对路径），
跟着布局落盘，原文格挂上时读参数、外壳顶掉预览格时经 `retarget` 软换。开法照外壳的手势约定——树格不是原文格，
所以单击是预览，Ctrl / 中键正式开一个新标签，Ctrl+Alt 开到旁边；开在哪归外壳（来源是树格，落在最近用过的那组
原文格里，没有就开到单元树旁边）：

## 拆成几块，依赖是单向的

```
scan.ts / browse.ts / current.ts     纯机 / 纯逻辑：只认 node:fs 与路径形状，不知道 cordis 存在
create.ts                            （create.ts 建单元，复用 scan.ts 的出生证校验）
          ↑
      index.ts                        cordis Service：把上面几块接到窗格、命令、服务面、事件上
          ↑
   client/index.tsx                   浏览器半：只经命令总线说话，不 import 宿主半一个符号
   client/units.ts                    （过滤与图标名换算的纯逻辑，tests/units.test.ts 测）
   client/open-file.ts                （点文件开成什么样的原文格：手势 → 开法、文件 → key 与参数，tests/open-file.test.ts 测）
          ↑
   别的件（消费方）                    inject('gwbUnitFolder')、on('unit-folder/selection')
```

置顶表的加与摘、`current()` 的回落规则、清单里找置顶——全是「喂输入看输出」，所以全在 `tests/current.test.ts` 里测，

## 两条判据

**配置与数据分家。** `units-root` 是人在设置面里手填的，所以是设置（`gwbSettings.define`）；置顶是人在树上
点图钉、件因这个动作自己写下的，所以是数据（`gwbData` 文档 `pinned`）。判据跟外壳把布局档落 data 是同一条。
设置项 `pinned-unit` 因此不存在，产物守卫钉着它不许回来。树格的过滤（筛选下拉里的状态与种类）两样都不是：它只住窗格内存，
重开窗格回到默认（藏起退役的、种类不限）。

**带路径参数的命令共用一堵墙。** 命令总线对外暴露（agent 经 MCP 也在调），参数不能默认是界面自己递来的
那份清单上的：每条都先解 `units-root`、再把路径验成根内的绝对路径，越出根的一律回「路径不在容器根内」：

墙其实有两道。词法那道管字符串：`..`、根外绝对路径、换盘符在 `path.relative` 的结果上现形。物理那道管
落脚点（2026-09-20 起）：NTFS 的 junction / symlink 不改字符串、只改落脚点，根内一条链接能把 `stat` /
`open` 带到根外去——已存在的路径要 `realpath` 解到实际位置再比一次边界，指到根外的一律拒；路径不存在时
物理那道不拦，「不存在」的错归下游报。校验后毫秒级把目录换成链接的竞态不防（纯 Node 拿不到句柄级
final-path），本机桌面威胁模型下不做：

## 怎么用

装：`plugin-manager.install {"pkg":"@godcreator/gwb-unit-folder"}`，或进 home `pnpm add` 再在 `cordis.yml` 手写一条 `id: unit-folder`
的条目（没有 `config`）。装完到「设置」填 `units-root`。确认它真在干活：日志里有 `服务就绪（ctx.gwbUnitFolder）`，
在树上点一个单元后 `unit-folder.current` 回那个单元的 `{ unitPath, unitName, path }`。开发循环与发版见仓根 README。
