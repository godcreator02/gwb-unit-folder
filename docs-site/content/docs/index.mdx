# 单元文件夹

**本页回答**：这个插件管什么、一次点击从头到尾怎么走、拆成几个模块、依赖为什么是单向的、怎么装。

`gwb-unit-folder` 是 gwb 内核线的一个插件。它管的是**「单元」这个纯目录约定在工作台里怎么呈现**：
容器根下一层一个目录、目录里一张 `unit.json` 出生证——这个插件建单元、把它们显示成一棵树（现扫、读出生证、按状态与种类过滤、
展开、看原文），并且**把「人现在看的是哪个单元」这个事实往外报**给别的插件。出生证的字段表以本插件为正本
（读盘与 `unit-folder.create` 共用一处校验），见 [服务与命令](/docs/service-and-commands#出生证-unitjson)。

这一页讲原理与模块划分；服务、事件与命令在 [服务与命令](/docs/service-and-commands)；
为什么是「往外报」而不是扩展点、置顶为什么从设置改成数据，在轨迹卡[「选中往外报」](/trajectory/2026-09-09-report-selection-not-extension-point)。

## 一次点击从头到尾怎么走

人在单元树窗格里点一个单元行。浏览器侧做两件事：本地展开那一行（目录清单经 `unit-folder.listDir` 现拉）、
发一条 `unit-folder.select { path }` 给 node 侧、不等回执。第二件事不等第一件，也不让第一件等它——
「当前单元」是给别的插件看的，报不上去不该让树本身卡住。

node 侧收到 `select`：先过路径检查——解设置里的 `units-root`、把参数路径验成容器根内的绝对路径——
再确认这个目录还在（不在直接回失败，不记下一个不存在的选中），然后按路径形状推出所属单元（relative 的第一段就是单元名），
记成「最近一次点击」；如果 `current()` 因此变了，就在自己的 ctx 上 `emit('unit-folder/selection', …)`。
消费方局部注入本插件、`on` 这条事件，就能跟着选中走。

记住的点击也会过期：单元目录被删了、容器根换了。`unit-folder.list` 每次现扫时顺带核对——最近一次点击的单元不在清单里，
就清掉这次点击，`current()` 随之回落，并广播一次 `unit-folder/selection`。

置顶走的是同一道路径检查，但结果存在别处：`unit-folder.pin { path }` 要求 path 是容器根下一层的单元目录，
追加进内存里那张置顶表、再写 `gwbData` 的文档 `pinned`（`{ paths }`）。置顶可以有多个；`current()` 没点过时回落到
第一个置顶，所以置顶在那种情况下也会让 `current()` 变、也会广播。

点的是文件就不报选中，而是开一个原文窗格。原文窗格是外壳眼里的**文档窗格**（能多开，一份装一个文件），单元树是
**工具窗格**（整页一份）。两个窗格之间不经命令总线：装哪个文件存在那一份原文窗格的参数里（key 是文件的绝对路径），
随布局保存，原文窗格挂载时读参数、外壳替换预览窗格的内容时经 `retarget` 原地换。开法照外壳的手势约定——单元树不是原文窗格，
所以单击是预览，Ctrl / 中键正式开一个新标签，Ctrl+Alt 开到旁边；开在哪归外壳（来源是单元树，开在最近用过的那组
原文窗格里，没有就开到单元树旁边）：

## 拆成几块，依赖是单向的

```
scan.ts / browse.ts / current.ts     纯逻辑：只认 node:fs 与路径形状，不知道 cordis 存在
create.ts                            （create.ts 建单元，复用 scan.ts 的出生证校验）
          ↑
      index.ts                        cordis Service：把上面几块接到窗格、命令、服务、事件上
          ↑
   client/index.tsx                   浏览器侧：只经命令总线通信，不 import node 侧一个符号
   client/units.ts                    （过滤与图标名换算的纯逻辑，tests/units.test.ts 测）
   client/open-file.ts                （点文件开成什么样的原文窗格：手势 → 开法、文件 → key 与参数，tests/open-file.test.ts 测）
          ↑
   别的插件（消费方）                  inject('gwbUnitFolder')、on('unit-folder/selection')
```

三条边界各自「不知道什么」：

**纯逻辑那层不知道 cordis 存在。** `current.ts` 里的函数——从路径推所属单元、选中前确认目录还在（判存在由调用方传入）、
置顶文档验形状、置顶表的加与摘、`current()` 的回落规则、清单里找置顶与最近一次点击——全是「传入输入、比对输出」，
所以全在 `tests/current.test.ts` 里测，`index.ts` 只负责接线。回落规则是整个服务的语义核心，它长这样：

## 两条判据

**配置与数据分开。** `units-root` 是人在设置界面里手填的，所以是设置（`gwbSettings.define`）；置顶是人在树上
点图钉、插件因这个动作自己写下的，所以是数据（`gwbData` 文档 `pinned`）。判据跟外壳把布局存进 data 是同一条。
设置项 `pinned-unit` 因此不存在，产物测试检查它不会再出现。单元树的过滤（筛选下拉里的状态与种类）两样都不是：它只存在窗格内存里，
重开窗格回到默认（藏起退役的、种类不限）。

**带路径参数的命令共用同一道路径检查。** 命令总线对外开放（agent 经 MCP 也在调），不能假定参数一定是界面从自己的
清单里传来的：每条都先解 `units-root`、再把路径验成根内的绝对路径，越出根的一律回「路径不在容器根内」：

{/* ref file="../plugins/unit-folder/src/index.ts" lines="291-303" hash="266ffdaf6831" blob="dd9ed334da73" */}

检查其实有两道。词法那道看字符串：`..`、根外绝对路径、换盘符在 `path.relative` 的结果上都看得出来。物理那道看
实际位置：NTFS 的 junction / symlink 不改字符串、只改实际指向，根内一条链接能把 `stat` /
`open` 带到根外去——已存在的路径要 `realpath` 解到实际位置再比一次边界，指到根外的一律拒；路径不存在时
物理那道不拦，「不存在」的错交给后面的步骤报。校验后毫秒级把目录换成链接的竞态不防（纯 Node 拿不到句柄级
final-path），本机桌面的威胁模型下不做：

## 怎么用

装：`plugin-manager.install {"pkg":"@godcreator/gwb-unit-folder"}`，或进 home `pnpm add` 再在 `cordis.yml` 手写一条 `id: unit-folder`
的条目（没有 `config`）。装完到「设置」填 `units-root`。确认它真在干活：日志里有 `服务就绪（ctx.gwbUnitFolder）`，
在树上点一个单元后 `unit-folder.current` 回那个单元的 `{ unitPath, unitName, path }`。开发循环与发版见仓根 README。
